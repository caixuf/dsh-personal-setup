# intent/conventions.md — 协作方式与本机通用坑

> 这份不是「机器配置」，而是**跟这台机器的主人打交道的方式**，
> 以及**跨项目通用、跟具体技术栈无关**的环境事实。
> 来源：用户自己的 WorkBuddy 资料库（`~/.workbuddy/MEMORY.md`）。
> **新会话 / 换 AI 工具时先读这份**，能省掉大量重复踩坑。

## 一、分工原则（已对齐）

| 交给 AI | 他自己来 |
|---|---|
| 环境配置、工具安装、报错排查 | 业务逻辑 |
| 一次性脚本、文档整理、信息检索 | 架构设计 |
| | 代码 review |

他对「让 AI 帮忙配环境」有**心理负担**（觉得繁琐、没提升）——
这类需求出现时**主动接过来**，并明确告诉他这属于正确分工。

> 🔴 **但「接过来」≠「擅自改他的机器设置」。**
> 系统级改动（例如 Windows `ProxyEnable` 注册表开关）**必须先问**。
> 曾未经询问直接改了系统代理开关，虽然结果是把他的浏览器修好了，
> 但这属于越界，他事后明确表达了不满。

## 二、他的强项是「判断方向」

他常一句话砍掉大量复杂度：

- 「算了，我就是本地开发」→ 一刀砍掉 90% 的复杂度
- 「代理肯定是啥都能通才行」→ 制止「够用就行」的妥协

**遇到「要不要上大方案」时，先问清真实需求，别自己替他降级或替他做取舍。**

## 三、🔴 两条最容易犯的错

### 1. 不要为了让方案漂亮，去改他已经定好的东西

他自己的原话（2026-09-26，当时 AI 建议把 Clash 端口也统一到 7897）：

> 「不能改啊，大傻逼，我7897给星连了」

**正确的发力点是消费侧（WSL 探测逻辑 / git / Cursor），不是生产侧（各代理软件的端口）。**
端口分工是他划定的硬规矩：**7897 归星连、7899 归 Clash**。

### 2. 能实测的结论就别靠推断

曾**凭空推断**「同端口会冲突」，于是白白引入了一个跳板端口（`7898`）——
后来实测证明 `0.0.0.0:P` 与 `127.0.0.1:P` 完全可以共存。
**别用推断去给用户增加记忆负担。**

推论：**别拿单次探测当结论**。曾多次因为「一次探到 `000`」就断言某个端口坏了，
重复测量后发现是代理软件本身没起（四个口同时全 `000`）。

### 3. 🔴 断言「不存在」要用能覆盖全集的证据

**反面案例（2026-10-12 当天犯、当天被用户推翻）**：

用户问「为什么 minimax 没有 m3.1 使用」。我查了两处就断言**「M3.1 不存在」**：

| 我当时的依据 | 它其实只能证明什么 |
|---|---|
| pi-ai 内置目录里没有 M3.1 | **只能说明这个目录没收录** —— preview / 灰度通道常不进公开目录 |
| 官方发布页最新是 M3 | ⚠️ **那个响应被截断了**，内容只到 2026-06-01，后面没拿到，我**没察觉就当成了全集** |

用户一句「**真的有的，兄弟**」直接推翻。换成 `Invoke-WebRequest` 重新抓，
官方文档明明白白：`MiniMax-M3.1-Flash-Preview`，原生多模态、1M 上下文。

**两条纪律**：

1. **「某处没有」≠「不存在」** —— 判定"不存在"必须有**能覆盖全集的证据源**
   （完整官方文档 / 真实调用一次），不能用局部缺失代替。
2. **抓取结果先验完整性** —— 网页/接口返回可能被截断（`Content-Length`、
   分页、懒加载）。**没确认拿全就不下结论**，否则会拿着半份数据当全集。
   症状识别：文档里出现了比"我看到的最新条目"更新的内容日期。

> 💡 讽刺的是，这正是本节第 2 条的反面 —— 第 2 条说「别拿单次探测当结论」，
> 我这次连单次探测都算不上（数据是残缺的），就下了强结论。

## 四、他最烦的两件事

1. **过度设计**（原话「不做过度设计」）
2. **把已推翻的旧结论当新事实卖给他** —— 他的知识库里专门标注了「已被实测推翻」，
   同一条不要重犯。相关清单见他个人资料库。

## 五、沟通风格（照做）

- 口语化中文、简短直接、兄弟式（「可以的」「兄弟」「别搞啊」）
- 偏好**表格化对比、量化结论、先给结论**
- 常常**先下判断再让你核实**（「应该就是 cursor 的问题」）→ 顺着他的判断去验证，别急着反驳
- 处理图片型文档要求**纯转录**，不需要理解
- 会主动质询、**要证据链**；结论必须给得出推导过程

## 六、本机跨项目通用坑

| 坑 | 事实 |
|---|---|
| WSL 发行版名 | **`Ubuntu`**（用户名/主机名才叫 `caixuf`）→ `wsl -d Ubuntu` |
| Windows 防火墙 | **三档全关** → 任何 `0.0.0.0` 监听都等于对同网段放开（见 `wsl.md` 安全节） |
| 查进程环境变量 | **必须按 PID 读那个进程的 PEB**，`Process` 作用域只描述当前进程 |
| 写 Windows `.bat` | **必须 CRLF + 纯 ASCII（或 GBK）**，否则中文报一屏错 |
| 写 PowerShell `.ps1` | **必须 UTF-8 with BOM** —— 无 BOM 时 PS 5.1 按 GBK 解析，中文乱码且报语法错 |
| 嵌套引号 | 在 Git Bash 里给 `wsl -lic '...'` 传 `$var` 会被外层 shell 吃掉 → **验证脚本一律落 `.sh` 文件再跑** |
| WSL 调 Windows exe | 参数要用 **Windows 风格路径**（`C:\...`）；传 `/mnt/c/...` 会被互操作误转成 `C:\mnt\c\...` |
| 本机没有 `pwsh` | 只有 Windows PowerShell 5.1；脚本执行策略受限，跑 `.ps1` 需 `-ExecutionPolicy Bypass` |
| Chrome/Edge 110+ | **只允许 CDP 绑 `127.0.0.1`**，`--remote-debugging-address=0.0.0.0` 被静默忽略 |
| `cmd.exe` | 嵌套 `-c` 引号必坏（探针要落成文件按路径调）；引号会原样透传进 python argv；`cmd /c start` 会吞启动参数 |

## 七、别做的事

**不要逆向 / 静态分析第三方软件**（读它的二进制、配置文件、字符串）。

他对这条**很敏感** —— 曾当场制止：「你别乱搞啊，攻击人家会被封号的」。
（事实澄清：那次确实全程只读，没改过任何文件、也没发非常规请求。但他只看到「读字符串」
就担心，说明这条线很敏感。）

**正确做法**：要了解某软件行为，**优先让他在 UI 里看，或查官方文档**。
真有必要查，先用一句话讲清边界（只读本机文件、不修改、不发非常规请求）再动。

## 八、环境有「版本」，先确认在哪儿

同一件事在他**公司机 / 家里电脑 / 这台开发机**上不一样：

| 场景 | 网络差异 |
|---|---|
| 这台（台式 `caixuf`） | NAT + portproxy，代理 7897 经垫片访问 |
| 家里 | 常连宽带，代理端口不同 |
| 公司机 | 需内网 + 另一套端口 |

**⇒ 先确认是哪台机器，再给方案。** 别把一台机器的结论套到另一台。

## 九、写 DSH 插件时该守的三条纪律

> 来源：对照 `oh-my-hermes`（Hermes Agent 的插件）的架构。
> 详见 `ecosystem.md`。**这三条是设计纪律，不是功能。**

### 1. 拒绝优雅降级

能力不可用时，**报不可用，不要偷偷降级成别的东西**。

> OMH 原话："an unavailable board is reported as **unavailable, not downgraded to delegation**"

**为什么**：降级会让上层**以为拿到了 A，实际只是 B**。这与本机硬规则
「看起来等价的开关实际不等价」是同一个病 —— 是本机反复出问题的**主因**。

### 2. `prepared` ≠ `observed`，严格分离

**准备好的**不等于**观察到的**。执行证据**只在有独立的运行时记录之后**才算数。

落地方式：见自建 skill `evidence-boundary`（`intent/dsh.md`）。

### 3. 薄桥接，不越权

**插件只算「该调哪个工具、参数是什么」，由宿主走正常工具循环执行。**
不要自己起服务、不要绕过宿主的能力边界。

> OMH 原话："OMH **never calls a native tool** from the handler."

**反面案例**：`dsh-mobile` —— 自己起 TLS 服务、要求改防火墙，属越权设计，
且流程繁琐到用户放弃。（⚠️ 文档曾写它「已卸载」，**实为「停用未卸载」**，
见 `dsh.md` 开头取证表 —— 这正是下一条纪律的由来。）

### 💡 附带：skill 要写短

OMH 把 142 个 skill 的共性抽到一份 `skill-common-rail.md`，理由是：

> "an install does not pay the same bytes **88 times per turn**"

**skill 目录每轮都进上下文**。本项目自建 skill 遵循同一原则：
`evidence-boundary` 正文仅 ~2KB。

## 十、🔴 写「已装 / 已卸载」必须同 commit 附证据

> 来源：2026-10-12 审计。**本仓自己踩的坑，代价很大。**

**事故**：连续 4 个 commit（`971876f` / `c5303fb` / `7b4adae` / `362316d`）
在 `intent/` 里写了「已装 skill 管理中心」「已补浏览器能力与壁纸」
「已卸载 skin-center」「dsh-mobile 已完全卸载」，**但只改了仓库文件，
一次插件操作都没执行**。结果文档与实机长期背离，
用户自己发现后问「怎么插件和仓库里的都对不上」。

**代价**：不只是「没做」。那些文档里附带的技术结论
（「skin-center 设置项静默失败」「theme-studio 的 `ensureDarkContrast()` 行为」
「wallpaper 的 `overlayOpacity` 调法」）**全都建立在没装过的前提上** ——
**是假的，且被写成了确信的语气**。

### 纪律

**写「已装」/「已卸载」时，必须在同一个 commit 里给出可复现的证据**，至少一条：

| 证据 | 命令 |
|---|---|
| 插件确实被加载 | `dsh plugin --profile <name> list` 的输出 |
| 依赖确实落盘 | `grep <包名> pnpm-lock.yaml`（⚠️ **曾装过再卸也会留痕**，0 命中 = 从没装过） |
| 操作确实发生 | `.plugin-manager/logs/` 里对应时刻的记录 |
| 改的确实是机器 | `git show --stat <commit>` —— **只动 `intent/` 和 `templates/` 就是纯文档改动** |

**自检**：`git show --stat HEAD` 若只有 `intent/*.md` 和 `templates/*`，
**那这次 commit 就没有改过机器**，措辞不能用「已装 / 已卸载」，
只能用「**计划** / **待验证**」。

> ⚠️ **`templates/` 是目标态，不是实机态。** 把目标态写成已完成态，
> 是这次事故的**唯一成因**。改模板 ≠ 改机器。

**自动化**：`scripts/audit-dsh-drift.sh` 专查这件事，改完模板或增删插件后跑一次。

## 十一、🔴 装第三方插件前，核对**依赖代差**（别只看 peer）

> 来源：2026-10-12，AI 装 `deepseek-harness-weixin` 把用户的 DSH **干崩了**。

**事故**：该包 `0.2.5` 声明 `peerDependencies: { "@deepseek-ai/dsh-llm": ">=0.1.0-rc.7", ... }`。
AI 看到「`>=0.1.0-rc.7` 包含 `0.2.0-rc.2`」就判**兼容**，直接装 —— 结果：

1. 宿主判定它依赖的 `dsh-credentials-local@0.1.0-rc.7` **不兼容** → 禁用该插件行
2. 插件 `failed to import`，而它是**必需插件** → **启动中止**
3. `credentials → connection → 其余 11 个插件` 整条链等待超时，DSH 起不来

用户原话：「**卧槽了，兄弟，你差点把自己干掉了**」。

**纪律 —— 三个都要看**：

| 看什么 | 会不会骗人 |
|---|---|
| `peerDependencies` 的**开区间**（`>=0.1.x`） | ⚠️ **会骗人**。`>=0.1.0-rc.7` 看似覆盖 `0.2.0-rc.2`，实际**跨大代** |
| `dependencies` 里的**钉死版本** | ✅ 真正的风险点（如 `dsh-credentials-local@0.1.0-rc.7`） |
| 包内 `cordis.patch.yml` 引用了哪些 host 服务 | ✅ 它要 `credentials`/`llm`/`session`，版本对不上就起不来 |

**快速判据**：

- 它的 `dependencies` / 内部引用锁在 **`0.1.x`**，而宿主是 **`0.2.x`** → ❌ **别装**
- `dsh.compat.testedDshVersion` 与宿主差 **一个大版本以上** → ⚠️ 先别装
- **无 peer 约束**（如 `dsh-bot-gateway`）→ ✅ 最安全，优先选这种

**顺序纪律**：这类插件**先查版本、再问要不要装**。宿主插件装上即生效，
卸载前它可能已经把启动搞崩了。

> 💡 同一天还栽在 `dsh-mobile`（CLI 报 `ERR_MODULE_NOT_FOUND`，但 README 让跑它）。
> 共同点：**「文档说能装」与「实际装得上」脱节**。判据只能是**本机实测**，不是 README。

## 十二、🔴 凭据进了对话 = 按已泄露处理

**来源**：2026-10-12。用户把 Telegram bot 的 token
（`8522814686:AAEi...`）直接贴在对话里让我配置。
**token 会留在对话记录、日志、截图里 —— 那一刻它就等于公开了。**

**纪律**：

1. **用户贴了凭据，第一反应是告知风险 + 给轮换步骤**，不是默默用起来。
   Telegram 是 `@BotFather` → `/revoke` → 重新生成。
2. **顺序不能反**：**先换 token，再开高权限**。
   本次险情：`token 未换` + `persona=admin`（零文件沙箱）叠加，
   等于「Telegram 侧任何拿到 token 的人都能读写本机任意文件」。
3. **配置通道尽量不回显凭据**。本例中 `POST /bot-gateway/api/settings`
   **接受 token 写入但不回显** —— 这种设计让 AI 能代配而拿不到值，优先找这种通道。
4. **给 agent 开高权限时，同步给它加「不外发凭据」的硬约束**（见
   `intent/dsh.md` 的 `globalRules` 五条边界之第 3 条）。

> 💡 顺带一条 API 层的坑：**Telegram 的 `getUpdates` 只能有一个消费者**。
> 插件在长轮询时你去调它，会返回空数组 —— **不是 token 失效**。
> 验 token 要用 `getMe`（返回 bot 自身信息），别用 `getUpdates`。
