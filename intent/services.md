## 1. litellm 模型网关（4001）

**用途**：把多个 provider（commandcode / Cline / Copilot 等）统一成一个 OpenAI 兼容端点。

| 项 | 值 |
|---|---|
| 配置 | `~/.config/litellm/config.yaml`（12 KB，**无硬编码密钥**，用 `os.environ/`） |
| 密钥 | `~/.config/litellm/proxy.env`（❌ 不入库） |
| venv | `~/.local/share/litellm-venv/` |
| 数据 | `~/.config/litellm/github_copilot/`（令牌，不入库） |

**⚠️ `config.yaml` 是生成物**：头部写着
```
# GENERATED by bridge/render_config.py — DO NOT EDIT.
# Source of truth: registry/models.yaml + registry/profiles.yaml
# Regenerate:  ccp render
```
**所以不要手改 `config.yaml`** —— 改源头（`registry/*.yaml`）再 `ccp render`。

**恢复步骤**：
```bash
# 1. 建 venv 并装 litellm
python3 -m venv ~/.local/share/litellm-venv
~/.local/share/litellm-venv/bin/pip install 'litellm[proxy]'

# 2. 配置（模板无密钥，可直接用）
mkdir -p ~/.config/litellm
cp templates/litellm/config.yaml ~/.config/litellm/config.yaml

# 3. 【手动】创建 proxy.env（见 secrets.md）
chmod 600 ~/.config/litellm/proxy.env

# 4. 启动
~/.local/share/litellm-venv/bin/litellm --config ~/.config/litellm/config.yaml --port 4001
```

**验证**：`curl -s http://127.0.0.1:4001/models -H "Authorization: Bearer <key>" | jq '.data[].id'`

## 2. ccp — 终端 LLM 环境统一管理

**用途**：切换 Claude Code / 各 CLI 的 provider 环境变量，避免在 `.bashrc` 里硬编码。

### ✅ 它有自己的仓库（**不要复制本仓库的内容**）

| 项 | 值 |
|---|---|
| **仓库** | **https://github.com/caixuf/claude-code-providers** |
| 本地克隆 | `~/code/claude-code-providers` |
| 分支 / 提交 | `main` / `6976456`（2026-10-09） |
| 一键安装 | `bash install.sh`（还有 `--bridge` 选项） |

**新机装法**：

```bash
git clone https://github.com/caixuf/claude-code-providers.git ~/code/claude-code-providers
cd ~/code/claude-code-providers
bash install.sh            # 装 ccp 到 ~/.local/bin + 初始化 ~/.claude/providers
# 若要 OpenAI / CommandCode / ClinePass 模型：
bash bridge/setup_bridge.sh
```

`install.sh` 会：
1. 把 `bin/ccp` 复制到 `~/.local/bin/ccp`
2. 检查 PATH 并提示（我们的 `templates/profile.d/` 已含此行）
3. 用 `providers/*.json.example` 初始化 `~/.claude/providers/`（**已存在的文件不覆盖**）
4. 归档废弃 profile 到 `~/.claude/providers_disabled/`

### 该仓库的密钥处理（规范，值得信赖）

`.gitignore` 已正确排除：

```gitignore
providers/*.json              # 真实 profile（含密钥）不入库
!providers/*.json.example     # 只留模板
bridge/config.yaml            # bridge 配置（含密钥）不入库
!bridge/config.example.yaml
```

**所以新机 clone 后只需填 `providers/*.json` 里的密钥**，不会继承旧机密钥。

### 目录与状态

| 项 | 值 |
|---|---|
| 可执行 | `~/.local/bin/ccp`（由 `install.sh` 从仓库 `bin/ccp` 复制） |
| 仓库 | `~/code/claude-code-providers` |
| 配置 | `~/.ccp/config.json` |
| 状态 | `~/.ccp/state.json` |
| 生成物 | `~/.ccp/env.sh`（**由 `ccp use` 生成，勿手改**） |
| 密钥 | `~/.ccp/secrets.env`（❌ 不入库） |
| profiles | `~/.claude/providers/*.json`（❌ 含密钥，不入库） |

**关键路径发现**：`ccp` 的 `sync_providers()` 按以下顺序查找仓库
（`CCP_REPO_DIR` 环境变量可覆盖）：

```
1. $CCP_REPO_DIR
2. $(dirname ~/.local/bin/ccp)/..        # 即 ~/.local
3. ~/code/claude-code-providers          # ← 命中
4. ~/.claude-code-providers
5. ~/claude-code-providers
```

**所以仓库必须放在 `~/code/claude-code-providers`**，否则 `ccp sync` 失效。

### 用法

```bash
ccp                        # 列出所有 provider（* 标记当前）
ccp <provider> [model]     # 切换 provider
ccp -c / --current         # 查看当前 provider / model / 端点
ccp -r [N]                 # 回滚到第 N 个最近备份
ccp -t [name]              # 快速测试（ping）
ccp sync                   # 与仓库模板同步 profile
ccp bridge <action>        # 本地 bridge 管理（status/restart/start/stop/logs）
ccp auth copilot           # Copilot 设备流认证
```

**当前 active**（实测）：`cmdc-deepseek-fast`（model `cmdc-deepseek-fast[1m]`）

**可用 provider 清单**（实测）：`cline-deepseek`、`cmdc-deepseek-fast`、`cmdc-deepseek-pro`、
`cmdc-deepseek`、`cmdc-vision`、`copilot`、`deepseek`、`minimax`

### `env.sh` 生成的内容（指向本地 litellm 4000）

```bash
export ANTHROPIC_API_KEY=sk-ccp-local     # ← 本地占位 key，非真实密钥
export ANTHROPIC_BASE_URL=http://127.0.0.1:4000
export ANTHROPIC_MODEL=deepseek/deepseek-v4.1-flash
```

⚠️ `ccp` 脚本自身**经检查不含任何密钥**（0 命中高置信特征），可安全经由其仓库分发。

**⚠️ 依赖关系**：`ccp` → 需要 litellm(4001) 起着 → 需要 `proxy.env` 的密钥。
三者顺序不能反。

### 浏览器怎么访问（2026-10-20 实测，踩过坑）

| 入口 | 可用性 | 说明 |
|---|---|---|
| `http://192.168.137.10:9900/` | ✅ | 网线段上那台设备；**浏览器必须绕过系统代理**才能打开 |
| `http://127.0.0.1:8080/` | ✅ | Windows 侧 `netsh portproxy`：`0.0.0.0:8080 → 192.168.137.10:9900` |
| `http://127.0.0.1:9900/` | ✅ | WSL mirrored 直接暴露（4ms） |
| `http://192.168.137.2:9900/` | ❌ 超时 | 本机「以太网」适配器自己的 IP，Windows 侧连它会挂 |

🔴 **「浏览器打不开、命令行 curl 正常」时先看绕过表**，别去查网络：
见 `intent/wsl.md` 的「浏览器访问内网 IP 报 502」一节。
浏览器读 WinINET 的 `ProxyOverride`，它被代理软件改残后会把内网地址
也交给代理 → 502；命令行读环境变量 `no_proxy` → 直连正常。
修法：`.\scripts\win-proxy-bypass.ps1 -Apply`（改完**重启浏览器**）。

`fetchAvailableModels` 全部秒通。真凶是 **Google CloudCode 服务端容量耗尽**：

```
UNAVAILABLE (code 503): No capacity available for model gemini-3.8-flash-high on the server
```

且 `gemini-3.8-flash` 的 SSE 流
（`daily-cloudcode-pa.googleapis.com/v1internal:streamGenerateContent`）
还会反复 `EOF` 卡死。

**实测可用 / 不可用（2026-10-20）**：

| 型号 | 状态 |
|---|---|
| `claude-sonnet-4-6` | ✅ |
| `claude-opus-4-6-thinking` | ✅ |
| `gpt-oss-120b-medium` | ❌ 503 无容量 |
| `gemini-3.8-flash-high` / `gemini-3.8-flash-low` | ❌ 503 无容量 |

`run.go:39 "attempt N failed"` 行 —— **503 = 服务端容量**（换型号或等），
**EOF = 长连接被掐**（再查代理/网络）。不要一上来就改代理配置。

**本机默认型号**已改为 `Claude Sonnet 4.6 (Thinking)`
（原 `Gemini 3.8 Flash (Medium)`），备份 `settings.json.bak.20261020_1700`。
改法就是改那个 `model` 字段的 label。

## 6. Hy Memory 2.0 —— 本地记忆服务（19527 + 19528）

> 2026-10-16 本机 WSL 实测跑通的**技术选型 spike**。它**没有**接进 DSH
> （没挂 `dsh-mnemon` 的任何 provider），目前是独立进程，**用不到可忽略**。
> 但它占两个端口且带一个密钥文件，换机清单里必须知道它存在。

**是什么**：腾讯混元开源的双系统认知记忆框架（Apache-2.0，PyPI `hy-memory`），
定位是 `dsh-mnemon` 之外的**另一条记忆路线**（本地优先，嵌入不外发）。

| 项 | 值 |
|---|---|
| 目录 | `~/hy-memory-spike`（**不在** `~/code/`，未接任何外部仓） |
| venv | `~/hy-memory-spike/.venv`（Python 3.12.3） |
| 版本 | `hy-memory==2.0.1`，`fastembed==0.9.0`，`fastapi==0.143.2`，`uvicorn==0.54.0` |
| 配置 | `~/hy-memory-spike/env.sh`（模板：`templates/hy-memory/env.sh`） |
| 嵌入 shim | `~/hy-memory-spike/embed_server.py`（模板：`templates/hy-memory/embed_server.py`） |
| 数据 | `~/hy-memory-spike/data/`（SQLite + 索引，全本地） |
| 密钥 | `~/hy-memory-spike/minimax.key`（chmod 600，**不入库**，见 `intent/secrets.md`） |
| 抽取 LLM | MiniMax 官方 API 直连（`https://api.minimaxi.com/v1`，模型 `MiniMax-M3`） |
| 嵌入 | 本地 CPU `BAAI/bge-small-zh-v1.5`，**512 维** |

**启动（当前是手动起的，没有 systemd 单元）**：

```bash
cd ~/hy-memory-spike && source env.sh
# ① 嵌入 shim（必须先起，19527 启动时要探它）
.venv/bin/uvicorn embed_server:app --host 127.0.0.1 --port 19528 --log-level warning
# ② 记忆服务本体
.venv/bin/python -m hy_memory.server --port 19527
```

**实测性能**：写入 3.5–5.4s / 条，召回 0.02–0.08s，数据全本地。

### 踩过的坑（别重复踩）

| 坑 | 现象 | 结论 |
|---|---|---|
| 经本机 LiteLLM(4000) + `cline-deepseek-v4-pro` 抽取 | 写入 **37–74s**；且被网关 400 拒（`system message must have content`，因其**空 system message**） | **直连 MiniMax**，两个坑一起消失 ⇒ 那是该模型的脾气，不是 hy_memory 不兼容 |
| 不加 `MEMORY_LLM_EXTRA_BODY` | MiniMax 把 `<think>` 塞进 content，污染抽取 JSON（completion 116→24 token） | 必须 `'{"thinking":{"type":"disabled"}}'` |
| `trae-*` 系模型（含 `trae-minimax-m3`）经网关 | 一律 `content=None` 不可用 | 直连那家的 `MiniMax-M3` |
| 自带 server 的 `/api/v1/add` **不透传 `scene`** | 自动路由把带 tool_calls 的编码轨迹判成 chat，facts/experiences/diff-chain 拿不到 | 要 coding/working 两层记忆**必须自己包一层 SDK** |
| 模型走本机 SOCKS 代理下载 | HF 拉不下来 | `pip install socksio` |
| `SIGTERM` 停不掉 hy_memory server | 忽略信号 | `ss -lptnH 'sport = :19527'` 找 pid 后 `SIGKILL` |
| 想在本机跑 30B-A3B 权重 | 没 GPU | ❌ 跑不了也不需要 —— SDK 只是 OpenAI 兼容客户端，权重是独立项目 |

> ⚠️ **MemHub 桌面端不支持 Windows**，只能在这台 WSL 里用。

**要不要接进 DSH 的判断依据**：它目前只是候选。若将来要接，
入口是 `dsh-mnemon` 的 provider 机制（见 `intent/dsh.md`），
届时需另开一条记录，本节只负责「换机怎么把它重建起来」。

## 服务启动顺序（重要）

```
Windows 代理软件启动（Clash Verge 7899；2026-10-22 前是星连 7897）
   ↓
WSL 启动 → fix-wsl-net.service 修正路由
   ↓
~/.bashrc → source ~/.proxy.sh → proxy_on（探测并设置代理）
   ↓
litellm 启动（4001）← 需要 proxy.env 的密钥
   ↓
ccp use <profile>（生成 env.sh，指向 127.0.0.1:4000）
   ↓
各 AI CLI 可用
```

**排查思路**：任何 CLI 卡住，从**最上游**查起（代理 → 路由 → litellm → ccp）。
